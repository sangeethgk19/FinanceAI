How to use this plan
Study these phases in order. Don't jump ahead. Each phase builds on the last. You don't need to master everything — you need to know enough to build. Learn by doing, not just reading. As soon as you understand a concept, immediately try it in code.
1
Python Foundations
Get comfortable before you touch anything AI related
Before June · 1–2 weeks
Variables, functions, loops, conditionals
The absolute basics. If you can write a loop, define a function, and handle an if/else — you're ready to move on. Don't overthink this.
Why: Every single file in your project uses these. You cannot build anything without them.
📚 Resource: Python.org beginner tutorial or freeCodeCamp Python full course on YouTube
Working with files and JSON
Reading and writing files in Python. Understanding what JSON is — it's just structured data that APIs use to send information back and forth.
Why: Your FastAPI sends and receives JSON. Your results get saved to CSV files.
📚 Resource: Real Python — "Reading and Writing Files in Python"
Installing libraries and virtual environments
How pip install works. What a virtual environment is and why you use one. How to create a requirements.txt file.
Why: You'll install 10+ libraries. Understanding this prevents hours of confusing errors.
📚 Resource: Just practice — create a venv, install streamlit, run hello world
Importing modules and basic project structure
How to split code across multiple files and import from one file into another. This is the foundation of modularity.
Why: Your project has 6 separate files that import from each other. You need to understand how this works.
2
What Are LLMs and SLMs
Understand what you're working with before you touch it
Before June · 3–4 days
What is a language model — conceptually
Not the maths. Just the concept. A language model predicts the next most likely word given everything before it. That's it. Read about tokens, context windows, and how models generate text one token at a time.
Why: You'll be asked this in your viva. You need to explain it clearly without jargon.
📚 Resource: "But what is GPT?" by 3Blue1Brown on YouTube — best visual explanation available
Difference between LLMs and SLMs
Large models (GPT-4, Claude) vs small models (Mistral, Llama, Phi-3). Parameters, size, capability tradeoffs. Why smaller models can run on laptops.
Why: This is the core justification of your entire project. You must be able to explain this.
📚 Resource: Read the introductions of the Mistral 7B and Phi-3 papers on ArXiv — just the abstract and intro sections
What is quantization
How models are compressed to run on smaller hardware. The GGUF format. Q4 vs Q5 — what the numbers mean. You don't need to understand the maths, just the concept of lossy compression applied to AI models.
Why: Ollama uses quantized models. Your dissertation literature review mentions this. Tony might ask about it.
📚 Resource: Hugging Face quantization guide linked in your project resources
What is a system prompt
How you give an AI model its personality and instructions before a conversation starts. The difference between system role and user role in a chat message.
Why: Your entire finance specialisation is done through a system prompt. This is your "training" substitute.
3
Ollama — Running Models Locally
The engine of your whole project
June Week 1 · 2–3 days
Installing Ollama and pulling models
Download Ollama, run ollama pull for each model, test them in terminal. Get comfortable with the CLI before writing any Python.
Why: If you can't get a model talking in terminal, you can't build the app around it.
📚 Resource: Ollama official GitHub quickstart — read and follow it completely
Ollama Python library
How to use ollama.chat() in Python. Understanding the messages list format — system role, user role, assistant role. How to extract the answer from the response object.
Why: This is the core of your api.py file. Every question goes through this.
📚 Resource: Ollama Python library README on GitHub — short and clear
Running Ollama as a server
The difference between ollama run (interactive terminal) and ollama serve (background server). Why you need ollama serve running before your FastAPI can work.
Why: Your whole app depends on Ollama running as a background service.
4
FastAPI — Building the API
The door between your interface and your models
June Week 1–2 · 3–4 days
What is an API and how HTTP requests work
What GET and POST requests are. What a URL endpoint is. What JSON request and response bodies look like. You use APIs every day — weather apps, Google Maps — now you're building one.
Why: You need to understand what FastAPI is actually doing before you write it.
📚 Resource: FastAPI official tutorial — first three pages only (installation, first steps, path parameters)
Creating a basic FastAPI endpoint
How to create an app, define a route with @app.post(), accept a request body, and return a JSON response. The automatic docs page at /docs.
Why: Your entire api.py is one endpoint. This is all you need to know.
Pydantic models for request validation
How to define what shape your incoming data must be using a Pydantic BaseModel class. What happens when invalid data is sent.
Why: Your Question class in api.py uses this to validate that every request has both a text and a model field.
Running FastAPI with Uvicorn
The uvicorn api:app --reload command. What --reload does. How to test your API using the /docs page.
Why: You'll type this command every single time you work on the project.
5
Streamlit — Building the Interface
Python that becomes a webpage automatically
June Week 2 · 2–3 days
Streamlit basics — text, inputs, buttons
st.title, st.write, st.text_input, st.button, st.selectbox. These five functions build 80% of your interface. Practice making a simple page before connecting it to your API.
Why: Your entire chat interface uses exactly these elements.
📚 Resource: Streamlit official 30 minute tutorial — do the whole thing
Streamlit layout — columns, tabs, sidebar
st.sidebar, st.tabs, st.columns. How to organise your page into sections. This is how you build the two-tab layout with the model selector in the sidebar.
Why: Your dashboard has a sidebar, two tabs, and metric columns. You need these three layout tools.
Connecting Streamlit to FastAPI using requests
How to use the requests library to send a POST request from your Streamlit app to your FastAPI endpoint and display the response. This is the moment everything connects.
Why: This is the single most important connection in your whole project.
Session state in Streamlit
Why Streamlit reruns your whole script every time something changes. How st.session_state lets you keep data between reruns — like storing chat history.
Why: Without session state your chat history disappears every time the user clicks Ask.
6
Pandas and Plotly — Data and Charts
Recording results and visualising them
June Week 3 · 2–3 days
Pandas basics
Creating a DataFrame, appending rows, reading and writing CSV files, groupby and mean for calculating averages per model.
Why: Your benchmark results live in a Pandas DataFrame saved to CSV.
📚 Resource: Pandas getting started — first three tutorials only
Plotly Express basics
px.bar for bar charts, px.scatter for scatter plots. How to set x, y, color, and title. How to display in Streamlit with st.plotly_chart.
Why: Your three benchmark charts all use Plotly Express — it's three lines of code per chart.
📚 Resource: Plotly Express getting started — bar charts and scatter only
Measuring time and RAM in Python
time.time() for measuring response duration. psutil.virtual_memory().used for RAM readings. How to calculate the difference before and after a function call.
Why: These two measurements are the core of your benchmark script.
7
Git and GitHub — Saving and Sharing Your Work
Version control and portfolio presentation
Ongoing from day 1
Basic Git commands
git init, git add, git commit, git push. That's genuinely all you need. Commit after every meaningful change with a clear message like "add benchmark script" or "fix timer display".
Why: Your supervisor expects a GitHub link. Employers look at your commit history to see how you work.
📚 Resource: GitHub's own Git handbook — 10 minute read
Writing a good README
What the project does, why it exists, how to install and run it, what you found in the benchmark. This is the first thing anyone sees when they visit your GitHub.
Why: A good README turns a GitHub repo into a portfolio piece. A bad one makes it look unfinished.
The order that matters
1. Python basics — loops, functions, files
2. What LLMs and SLMs are — conceptually
3. Ollama — install, pull models, test in terminal
4. FastAPI — one endpoint, test on /docs page
5. Streamlit — basic page, then connect to FastAPI
6. Pandas — record results, save CSV
7. Plotly — three charts from your CSV
8. GitHub — commit everything as you go
The golden rule: After studying each topic for 30 minutes, close the tutorial and try to write the code yourself from memory. Getting it wrong and fixing it teaches you 10x more than reading does.
